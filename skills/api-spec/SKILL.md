# API 規格文件

產出能讓呼叫端直接使用、維護者能對照實作的 API 文件。沿用使用者與 repository 的明確約定；以下為預設格式，不藉由寫文件改動 API 行為。

## 先確認契約

- 讀取適用的 `AGENTS.md` 與既有文件，再追查 route、request DTO、handler、service、repository 及相關測試。沿用專案既有的程式探索工具。
- 以實際程式碼為準，核對 method／path、欄位驗證、判斷順序、資料存取與每個回應分支。測試與程式不一致時，指出差異，不挑一份當作已證實的行為。
- 使用者明確提供的未實作需求可寫為設計，但必須和目前行為分開。沒有成功流程、只回 `501` 時，直接記錄現況，不虛構成功 JSON、寫入或副作用。
- 文件工作不自動包含實作 API、修改資料庫、安裝套件或發布文件；需要範例時使用合成資料，不拿真實寫入驗證文件。

## 位置與寫法

- 新文件預設放在 `docs/api/<路由群組>/<method>-<endpoint>.md`，路由群組可有多層；既有專案的層級與命名優先。例如 `POST /events/reports/export` 對應 `docs/api/events/reports/post-export.md`。
- 以繁體中文撰寫；識別字、欄位、路徑、HTTP method／status、error code 及正式產品名稱保留原文。
- 說明端點本身特有的權限或開放條件；不在每份端點文件重複全域 API key／token 驗證、ingress 或 CORS 設定。
- 不放入 secret、實際憑證、私人連線資訊或真實個資。更新既有文件時，修正相對連結，不為套用格式而搬動無關文件。

## 章節順序

```text
# <功能> API
## 端點
## 使用流程
## 請求
## 成功回應
### 回應欄位
## Agent 函式工具
## 處理流程
## 資料庫持久化結構
## 錯誤回應
```

沒有 Agent tool 時省略「Agent 函式工具」；沒有資料存取時可省略資料庫章節。沒有回應內容時不硬補欄位表；不要留下空章節或未替換的模板文字。

### 端點與使用流程

- 「端點」寫完整 `METHOD /path`，用一小段話說明用途、支援範圍與目前限制。
- 「使用流程」使用 Mermaid `flowchart TD`，從收到 request 畫到所有實際回應。
- 驗證、資料存在與否、外部查詢成功與否、業務條件、寫入／產檔成功與否等判斷使用 `{菱形節點}`；分支標示「是／否」或具體條件。
- 保留實際判斷順序，標出失敗回應的 HTTP status 與 error code。只畫實作或明確設計中存在的判斷，不套入沒有的查詢、權限或寫入。
- 圖中的分支必須能對應到「處理流程」及「錯誤回應」。

### 請求

依實際輸入分別描述 path、query、body，標示 `Content-Type`，並使用下列表格：

| 欄位 | 型別 | 必填 | 預設值 | 驗證規則 |
| --- | --- | --- | --- | --- |

- 巢狀欄位用 `records[].number` 這類路徑，列出陣列長度、重複值、enum、大小寫、格式及欄位間關係。
- 區分缺少欄位、`null`、空字串與 `0`；區分數字與數字字串、整數與浮點數。只記錄實際限制，不替分數等數值增加範圍。
- 提供符合表格規則的 JSON 與可執行 curl；GET、multipart 或其他格式依契約調整，不強塞 JSON body。主機及 port 沿用專案設定。

### 成功回應與回應欄位

- 寫實際 HTTP status、`Content-Type` 與成功範例，沿用專案既有的 envelope，不為統一文件改造回應格式。
- JSON 回應的欄位表使用「欄位、型別、說明」，展開巢狀欄位，說清楚 nullable、單位、時間格式、範圍及欄位間關聯。
- `204` 等無 body 回應直接說明。尚未實作成功流程時標示實際暫回狀態；錯誤欄位留在錯誤章節，不當作成功 schema。
- 下載端點記錄二進位內容、`Content-Disposition` 及檔名規則，不包成 JSON。Excel 等匯出另外說明頁籤名稱與順序、欄位、分組、排序、同分、null、篩選與底色語意，以實作為準。

### Agent 函式工具與處理流程

- 端點確實呼叫 Agent tool 時，列名稱、用途、輸入／輸出、強制順序、次數限制，以及失敗與空結果行為；連到實際存在的完整 tool spec。
- 「處理流程」以編號步驟描述實際先後：輸入驗證、前置條件、外部查詢、運算、寫入／產檔、回應與錯誤處理。
- 實作有 timeout、重試、取消、dry run、review 或部分成功等行為時才記錄，並對應流程圖。框架與內部函式名稱只在有助於定位行為時加入。

### 資料庫持久化結構

- 明確說明唯讀或有寫入，即使唯讀也列出讀取路徑、條件與使用欄位。
- 說明 collection／table、document／row ID、API 欄位到儲存欄位的映射，以及 reference／foreign key 關係。傳入編號、資料庫 ID 與顯示編號要分清楚。
- 欄位表使用「欄位、資料庫型別、來源與規則」。時間欄位記錄型別、時區、由誰產生，以及建立／更新時是否保留原值。
- 寫入端點記錄寫入條件、transaction／batch 邊界、重複資料或重送策略；存在主資料與稽核快照時，分別說明用途。
- 查詢有分頁、排序、limit、索引、快取或快照限制時據實描述；必要時說明刪除 parent 是否清理子資料。
- 不假設 Firestore、SQL、特定 ID 策略或 server timestamp 適用所有專案；只寫已驗證的實作，未知處標示待確認。

### 錯誤回應

使用下列表格，訊息及條件對應實作，不只寫「失敗」：

| HTTP status | error code | 訊息 | 觸發條件 |
| --- | --- | --- | --- |

提供專案實際的錯誤 JSON 範例；例如專案採 `{"error":{"code":"...","message":"..."}}` 時保持此格式。不要把 SDK 內部錯誤當作公開訊息，也不要新增實作沒有回傳的 error code。

## 交付前核對

- 從每個實際回傳點反查圖、表格與處理步驟：狀態、error code、驗證順序與副作用一致，且沒有把規劃寫成已完成。
- JSON／curl 與欄位表一致；nullable、0、重複值、排序及同分等端點相關邊界有明確語意。檔案下載的 header、檔名與內容結構一致。
- 檢查 Markdown 表格、Mermaid 節點與分支標籤，以及文件間相對連結。只修正本次文件範圍，不把文件整理擴大成程式或資料改造。
- 交付文件路徑，簡短說明整理內容及未能核對的資訊；不聲稱已呼叫正式 API 或驗證遠端資料，除非確實已做且在授權範圍內。
