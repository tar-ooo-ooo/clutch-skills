# MR／PR 小幫手

使用繁體中文，依最終變更撰寫精簡、具體且讓審查者看得懂的標題和描述。建立前確認來源與目標分支、提交內容及使用者要求的工作範圍，並查找適用的 repository 指引和 MR／PR 範本；範本有其他必要欄位時補上，工單資訊仍置頂。

## 確認工單

• 使用者已明確提供本次 MR／PR 的工單，直接採用，不重複確認。
• 使用者沒指定時，先從對話與變更脈絡尋找可能的工單；找到候選時，提出編號或連結並請使用者確認是否適用本次 MR／PR。
• 找不到候選時，詢問工單編號或連結，並說明可回答「無」或「沒有」。使用者回答無工單時，不顯示工單項目及空白佔位符。
• 在取得確認、明確單號或「無」之前，不自行猜測工單，也不建立 MR／PR。對話中的其他專案或任務單號不代表本次工單。

## 描述格式

有工單時，描述的第一項是 `工單：<使用者提供或確認的編號／連結>`；有已知連結時使用連結，不要自行猜測網址。接著以條列呈現變更摘要：每一項以簡短主題開頭，再說明實際變更與結果，例如「操作」、「資料處理」或「邊界」；主題依實際變更決定，不強制填入不適用的項目。必要時先交代觸發情境，讓未參與討論的審查者能理解。每個條目只描述一個重點，避免空泛措辭、重複內容與過長段落。多個並列重點使用 `•`，有先後順序的步驟使用數字編號。

```text
工單：<編號或連結>

## 摘要
• <主題一>：<改了什麼，以及使用者或系統會有什麼變化>
• <主題二>：<另一項變更及審查所需的行為或限制>

## 驗證
• <實際完成的驗證；尚未驗證的項目明確標示>
```

範例只示意格式：無工單時移除第一項；依任務需要調整項目數，不使用空章節，不虛構測試或結果。檢查 MR／PR 平台的顯示格式，確保條列項目能分行閱讀。

## 執行範圍

僅要求草稿時只提供標題與描述；使用者要求建立 MR／PR 時才建立，建立後回報連結與狀態。不要擅自合併、啟用自動合併或修改指派設定；建立 MR／PR 需要推送來源分支時，在使用者授權範圍內處理。使用者的明確要求優先。
