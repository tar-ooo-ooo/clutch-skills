# 工單留言格式

使用繁體中文，簡短、具體、方便掃讀；精簡不等於省略操作方式、關鍵技術或邊界。每次只使用一種分類。以使用者指示與實際資料為準，不虛構規格、進度、錯誤原因或驗證結果；規劃與已完成內容分開。

## 選擇分類

- 使用者明確指定 `#spec`、`#plan`、`#sum` 或 `#bug` 時，直接使用該分類，不再詢問分類。
- 未指定時，依工單、對話與任務脈絡推薦最適合的一種，簡短詢問使用者是否採用該分類；得到確認或其他選擇後再撰寫或修改。不要把時間經過視為確認。
- 若使用者在後續訊息更改分類，依最新指示處理；不要因自行推測而套用不同分類。

## 分類格式

使用者指定分類時仍辨識 # 標籤，但不輸出 # 標籤。依留言平台選用格式：

- GitHub 或 GitLab：使用 Markdown 標題（如 `## Bug`、`### 一句話解釋`）及 `- ` 無序清單；有先後順序的步驟使用 `1.`、`2.`、`3.`。分類與段落名稱沿用對應參考檔，將其【】標題轉為 Markdown 標題。
- 其他平台：每則留言第一行用【規格】、【預計開發】、【總結】或【Bug】對應標題；並列重點使用「•」，有先後順序的步驟使用 1.、2.、3. 編號（不用 - 前綴）。

每個重點獨立一項。只寫和該分類有關的資訊，避免重複既有留言，但必須保留讀者理解操作與設計所需的重點；不硬填未知、不適用或使用者未要求的內容。

選定分類後，只讀取對應的檔案：

- `#spec`：[references/spec.md](references/spec.md)
- `#plan`：[references/plan.md](references/plan.md)
- `#sum`：[references/summary.md](references/summary.md)
- `#bug`：[references/bug.md](references/bug.md)

## 編輯與發送

先讀取相關工單及既有留言，以避免重複並確認上下文。修改既有留言時先確認工單 ID 與留言／事件 ID，保留不在修改範圍的內容與附件引用；若介面採整則覆寫，提交前檢查完整新內容。僅在使用者要求或明確授權發送、修改留言時才寫入，送出後確認結果；單純要求草稿時只提供文字。
