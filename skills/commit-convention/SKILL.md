# Commit 訊息規範

使用以下格式，type 和 scope 都不可省略，冒號後接一個空格及簡短摘要：

```text
<type>(<scope>): <摘要> (#<單號>)
```

• `type` 依主要變更選擇適當類型，例如 `feat`、`fix`、`hotfix`、`refactor`、`docs`、`test`、`chore`、`style`、`perf`、`build` 或 `ci`。
• `scope` 是這次修改的模組或功能，依變更內容使用簡短、具辨識度的名稱，例如 `auth`、`wbs` 或 `issue-brief`。
• 摘要簡潔說明實際完成的變更；保留使用者要求的語言及其他明確格式要求。
• 有工單時，在摘要結尾加空格與 `(#123)`；沒有工單時，整段單號及括號都省略。

## 確認工單編號

• 使用者已明確提供這次 commit 的單號或已表示沒有單號時，直接使用該答案，不重複詢問。
• 上下文可推測單號但使用者尚未確認適用這次 commit 時，提出該候選號碼，詢問是否使用；不要自行當作已確認。
• 上下文沒有可推測的單號時，詢問使用者提供單號，並說明可以回答「無」或「沒有」；收到這類回答時不加單號與括號。
• 在收到有效確認或「無」的答覆前，不要猜測單號，也不要建立 commit。使用者只要求建議訊息時同樣先確認單號，但不執行 commit。

範例：`feat(wbs): 支援工作項快捷鍵移動 (#123)`；無單號時：`feat(wbs): 支援工作項快捷鍵移動`。

撰寫前查看相關變更與既有專案規範，依實際內容選擇 type、scope 和摘要。使用者提供明確訊息或格式時，以使用者指示為準。
